# Database nativity

Nova treats the database as part of the language, not a library you bolt
on. Two pieces: schema-first model generation, and a typed query builder
whose column references are checked at compile time.

## `nova db pull`: the schema becomes Nova types

```bash
./nova db pull --dsn sqlite:///app.db --out models.nova
```

This inspects the database with stdlib `sqlite3` and generates:

1. **`models.nova`** — one `data class` per table, plus a `fromJson`
   constructor per model:
   ```nova
   data class Post(id: Int, title: String, body: Option[String], views: Int)

   fn postFromJson(j: Json) -> Result[Post, String] { ... }
   ```
   Type mapping: `INTEGER` → `Int`, `REAL` → `Float`, `TEXT` → `String`,
   `BLOB` → `String` (decoded latin-1 — documented, not silent),
   nullable columns → `Option[T]`, `PRIMARY KEY`/`NOT NULL` → bare `T`.
2. **`.nova-schema.json`** — next to the output file. `nova check` reads it
   to validate table/column names (below).

Regenerate, don't hand-edit — the file says so at the top.

## Typed queries, checked at `nova check` time

```nova
let db = dbOpen("sqlite:///app.db", io)?
let rows = dbTable(db, "posts")
  .select(["id", "title"])
  .where("views", ">", 50)
  .orderBy("views", "desc")
  .all()?
```

- `dbTable(db, "posts")` — unknown table `"postz"` is **E_DB_SCHEMA** at
  check time (when `.nova-schema.json` exists).
- `.where("titl", "=", x)` — unknown column is **E_DB_SCHEMA**.
- `.where("views", "~~", x)` — unknown operator is **E_DB_SCHEMA**
  (allowed: `=`, `!=`, `<`, `>`, `<=`, `>=`, `like`).
- `.all()` → `Result[List[Json], String]`; `.first()` →
  `Result[Option[Json], String]`. Rows are `Json`; the pulled
  `postFromJson` maps them onto your model types.
- `.all()`/`.first()` need the `io` effect (they do IO); they take no
  capability argument — the `Db` handle from `dbOpen` carries it.
- `dbExec(db, "CREATE TABLE ...", io)` runs DDL/DML, returning
  `Result[Int, String]` (rows affected).

The checking is **best effort and honest about it**: it only fires when
the table/column/operator are string literals *and* `.nova-schema.json`
exists next to the entry file. Dynamic names skip the check silently —
a runtime `DbError` is still raised as `Err`, never a crash.

## What "sqlite only" means

`dbOpen` supports `sqlite:///` DSNs. Anything else fails honestly:

```
$ ./nova db pull --dsn postgres://user@host/db --out models.nova
db pull failed: postgres needs a driver (see docs/v2.1-database.md)
```

**Postgres/MySQL need a driver.** Python's stdlib has no postgres/mysql
client, and Nova is stdlib-only by design in v2.1. The interface is ready
— `db.py:parse_dsn` is the seam where a driver plugs in — but we do not
ship one, and we do not pretend `sqlite://` is a production database
story. The query builder generates parameterized SQL (`?` placeholders),
so the injection story is sound when drivers arrive.

## Example

`examples/db-demo.nova` (with `examples/blog.db`, `examples/blog_models.nova`
generated by `nova db pull`) runs end to end:

```bash
./nova run examples/db-demo.nova
# popular posts:
#   #1 Hello Nova (150 views)
#   #2 Boot (89 views)
# user 2: Grace
```

`showcase/blog` builds a full Blog API on pulled models.
